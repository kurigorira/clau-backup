# 要件定義書：院内Webサーバー NAS日次バックアップ・復元

| 項目 | 内容 |
|---|---|
| 作成日 | 2026-09-25 |
| 版数 | 1.0 |
| 作成者 | （仮）システム担当 |
| 想定利用開始 | （仮）2026年10月 |

## 1. 背景と目的

### 1.1 現状の課題
- 電子カルテのネットワーク（インターネットに接続していない閉域網）上に、独自のWindowsサーバーを立てている。Apache 2.4、PHP、MySQL、SQLiteが動いていて、ドキュメントルートは `C:\apache24\htdocs`。
- サーバーの故障、誤操作、ランサムウェアなどでデータを失ったとき、決まった手順で元に戻す仕組みがない。（仮・要確認：今の手作業バックアップの有無）
- 閉域網なので、クラウドにバックアップを置く方法は使えない。

### 1.2 このシステムで実現すること
毎晩自動で、院内のNASにDB・プログラム・設定のバックアップを取る。障害が起きたら、スクリプト1本で「前日（または過去の任意の日）の状態」に戻せるようにする。

### 1.3 期待効果
| 指標 | 現状 | 目標 |
|---|---|---|
| 障害時に失われるデータの範囲（RPO） | 不定 | 最大1日分 |
| 復旧にかかる時間（RTO） | 不定（手順なし） | DBだけ／htdocsだけなら30分以内。サーバーを作り直す場合は半日以内（仮） |
| バックアップ失敗に気づくまでの時間 | 気づけない | 翌朝の始業時 |

## 2. 利用者と利用シーン

| 利用者区分 | 人数 | 主な操作 | 利用頻度 | 利用端末 |
|---|---|---|---|---|
| システム担当者 | 1〜2名（仮） | 失敗通知の確認、月1回の復元テスト、障害時の復元 | 毎朝の確認（1分程度）、月1回 | 対象サーバー本体 |
| 代わりの担当者（担当者が不在のとき） | 1名（仮） | 手順書を見ながら復元する | 障害時のみ | 対象サーバー本体 |

### 2.1 主要な利用シーン
1. **毎晩2:00**：タスクスケジューラが `backup.ps1` を実行し、NASの `daily\yyyyMMdd_HHmmss\` に保存する。
2. **翌朝**：担当者がサーバーのデスクトップとNASに `BACKUP_FAILED_*.txt` や `BACKUP_WARN_*.txt` がないか確認する。あれば中を読んで対応し、ファイルを削除する。
3. **障害時**：`restore.ps1 -List` で世代を選び、まず別名に試し復元して中身を確認してから、`-Overwrite` で元の場所に戻す。

## 3. 機能要件

| ID | 機能名 | 概要 | 優先度 | 利用者 |
|---|---|---|---|---|
| F-01 | MySQLバックアップ | DBごとに `mysqldump --single-transaction` でダンプを取る | Must | 自動 |
| F-02 | SQLiteバックアップ | `sqlite3 .backup` でオンラインバックアップを取り、整合性をチェックする | Must | 自動 |
| F-03 | ファイルバックアップ | htdocs、Apacheの設定、php.ini、my.ini、その他の重要フォルダを robocopy でコピーする | Must | 自動 |
| F-04 | 世代管理 | 日次14世代＋月次12世代。古い世代は自動で削除する | Must | 自動 |
| F-05 | 検証 | ダンプが最後まで書かれたかの確認、SHA-256の照合、SQLiteの integrity_check | Must | 自動 |
| F-06 | 失敗・警告の通知 | NASとデスクトップに通知ファイルを置き、イベントログにも記録する | Must | 担当者 |
| F-07 | 復元 | 一覧表示、確認用の取り出し、DBを別名に試し復元、上書き復元（上書き前の状態は自動で退避） | Must | 担当者 |
| F-08 | 急な縮小の検知 | 前回よりダンプのサイズやファイル数が半分未満になったら警告する（誤削除・ランサムウェアの早期発見） | Should | 自動 |
| F-09 | アカウント権限の控え | MySQLのユーザーと権限の一覧を保存する（新しいサーバーに作り直すときの参考） | Should | 自動 |
| F-10 | バージョン記録 | Apache、PHP、MySQL、SQLiteのバージョンを記録する | Could | 自動 |

### 3.1 主要機能の詳細

#### F-01 MySQLバックアップ
- **入力**：`config.ps1` の `MySqlDatabases`（空なら、システムDB以外のすべてのDB）
- **処理**：DBごとに `--single-transaction --quick --routines --triggers --events --hex-blob --default-character-set=utf8mb4` でダンプを取る。ダンプはまずローカルの `C:\backup\work\latest\` に作り、NASに転送したあとSHA-256で照合する。
- **出力**：`mysql\<DB名>.sql`、`mysql\_grants.sql`、`manifest.json`（DBごとの文字コード・照合順序・ハッシュ）
- **受け入れ条件**：
  - InnoDBのDBを更新している最中に実行しても、エラーなく終わること
  - ダンプの最終行に `-- Dump completed` がない場合は失敗扱いになること
  - `restore.ps1 -AsDatabase` で別名のDBに戻したとき、テーブル数・件数・日本語データが元と一致すること

#### F-02 SQLiteバックアップ
- **入力**：`SqliteFiles` に列挙したファイル、および `SqliteSearchRoots` の下で見つかったファイル（ファイルの先頭16バイトでSQLiteか判定する）
- **処理**：`.backup` でコピーする。コピーはDELETEモードに変換してから `PRAGMA integrity_check` を実行する。元のジャーナルモード（WALなど）は記録しておく。
- **受け入れ条件**：
  - PHPが書き込み中でも、壊れていないコピーが取れること（integrity_check が `ok` を返す）
  - 復元したとき、元がWALモードだった場合はWALモードに戻ること

#### F-03 ファイルバックアップ
- **受け入れ条件**：日本語のファイル名や深い階層（260文字超）もコピーされること。`Exclude` に書いたパターンはコピーされないこと。

#### F-04 世代管理
- 日次：成功したものを新しい順に14世代残す
- 月次：その月の最初に成功したものを `monthly\` にコピーし、12世代残す
- 失敗分（`*_FAILED`）：14日で削除する。中断分（`*.partial`）：1日で削除する
- **受け入れ条件**：15回目の成功で、最も古い日次の世代が削除されること。失敗が続いても、成功した世代は削除されないこと。

#### F-06 失敗・警告の通知
- **受け入れ条件**：NASの接続を切った状態で実行すると、デスクトップに `BACKUP_FAILED_*.txt` ができ、終了コードが1になること。

#### F-07 復元
- **受け入れ条件**：
  - `-Overwrite` を付けないと、元の場所は一切変更されないこと
  - `-Overwrite` を付けたときは、`YES` と入力しない限り実行されないこと。上書き前の状態が `C:\backup\pre-restore\<日時>\` に残ること
  - NAS上のバックアップファイルのハッシュが一致しない場合は、何も変更せずに中止すること

## 4. スコープ外（今回作らないもの）

| 項目 | 理由 | 将来対応 |
|---|---|---|
| クラウドやインターネットへのバックアップ | 閉域網のため | 対応しない |
| OSを丸ごとイメージバックアップすること | Windows Server Backupの機能で別途取る | 検討 |
| 電子カルテ本体のデータ | ベンダーの管理範囲 | 対応しない |
| レプリケーション・冗長化 | 停止許容時間が半日程度なので不要（仮） | 検討 |
| メール通知 | 閉域網でSMTPがない想定 | 院内にSMTPがあれば検討 |
| 世代ごとの差分・増分バックアップ | 容量が数GB規模なら毎回フルコピーで十分（仮） | 容量が増えたら検討 |

## 5. 非機能要件

| 分類 | 要件 |
|---|---|
| 性能 | 1回あたり30分以内（仮：DB数GB以下、htdocs数GB以下） |
| 可用性 | バックアップ中もWebサービスを止めない（InnoDBと`--single-transaction`、SQLiteの`.backup`による） |
| セキュリティ | MySQLはSELECTなど読み取り権限だけのアカウントを使う。パスワードは `C:\backup\secure\*.cnf` に置き、NTFS権限でAdministratorsと実行アカウントだけが読めるようにする。NASの共有フォルダはバックアップ専用アカウントだけが書き込めるようにする |
| データ保全 | 日次14世代＋月次12世代＋ローカルに直近1世代（DBのみ）。NASのスナップショット（仮・要確認） |
| データ保持 | 最長12か月。それより古いものは自動で削除する |
| 運用・保守 | 失敗通知は毎朝確認する。復元テストは月1回（別名DBへの試し復元）。手順書は `docs\復元手順書.md` と、印刷してサーバーの近くに保管する |
| 拡張性 | 対象のDB・フォルダは `config.ps1` の配列に追加するだけで増やせる |

## 7. システム構成（案）

- **稼働環境**：対象のWindowsサーバー（Apache24、PHP、MySQLと同じ機械）→ 院内NAS（SMB共有）
- **技術構成**：Windows PowerShell 5.1、タスクスケジューラ、robocopy（すべてWindows標準）＋ mysqldump / mysql（インストール済み）＋ sqlite3.exe（単体の実行ファイルを1つ置く）
- **既存システムとの関係**：Webアプリには手を入れない。二重入力は発生しない
- **選定理由**：追加のソフトを入れずに、1人で保守できる構成にした。スクリプトは日本語のコメント付きのテキストなので、担当者が代わっても中身を読める

```
[Windowsサーバー]                                    [NAS \\NAS01\backup\webserver]
  MySQL   --mysqldump-->  C:\backup\work\latest\  ──┐    daily\20260925_020000\
  SQLite  --.backup---->  （直近1世代）             ├──>   mysql\ sqlite\ files\ manifest.json
  htdocs, conf, ini  ------------ robocopy --------─┘    monthly\...  logs\  LAST_SUCCESS.txt
  タスクスケジューラ 毎日2:00 → backup.ps1                  BACKUP_FAILED_*.txt（失敗時）
```

## 8. 制約条件・前提

| 区分 | 内容 |
|---|---|
| 技術的制約 | インターネットに接続できない（ツールは院外で入手して、院内のルールに沿って持ち込む） |
| 組織的制約 | NASの共有フォルダ作成・アカウント発行はNASの管理者に依頼する。院内の情報セキュリティ担当者の承認（仮） |
| 前提条件 | MySQLのテーブルはすべてInnoDB（確認済み）。NASの空き容量が「1世代の容量 ×（14＋12）× 1.2」以上あること |

## 9. リスクと対応

| リスク | 影響度 | 対応方針 |
|---|---|---|
| ランサムウェアがサーバー経由でNAS上のバックアップも暗号化する | 大 | NASのスナップショットを有効にする。使えない場合は週1回、外付けHDDにコピーして抜いて保管する（未決 #2）。NASの共有フォルダは、職員の普段のアカウントからは書き込めないようにする |
| バックアップは取れているが、戻せない | 大 | 月1回、別名DBへの試し復元を行う（手順書の「月次の復元テスト」） |
| 失敗通知に誰も気づかない | 中 | 毎朝の確認を担当者の業務に組み込む。NASの `LAST_SUCCESS.txt` の日付でも確認できる |
| 担当者の異動・退職 | 中 | 手順書をサーバーの近くと共有フォルダに置く。代わりの担当者が年1回、手順書を見ながら試し復元をやってみる |
| NASの容量不足 | 中 | 月1回、NASの管理画面で空き容量を確認する |

| フェーズ | 内容 | 目安 | 完了条件 |
